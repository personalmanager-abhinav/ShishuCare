# Product Discovery Platform — Architecture and Implementation Plan

**Date:** 16 September 2026  
**Status:** Proposed architecture; implementation not started  
**Initial scale:** 50–60 products, 200–300 visitors/day  
**Primary objective:** Help visitors discover products and choose an external marketplace.

## 1. Executive architecture summary

Build a statically generated product catalogue on Cloudflare, with a small serverless API for semantic search and anonymous event ingestion.

Maintain products as version-controlled JSON files. Generate product pages, a lightweight lexical search index, and product embeddings during the publishing process.

For semantic search, embed the visitor’s query using an inexpensive hosted embedding model and compare it directly against the 50–60 precomputed product vectors. Apply explicit price, category, and attribute constraints separately.

Store accepted behavioral events in Cloudflare D1. Aggregate them on a schedule, retain a bounded raw-event archive in private R2 storage, and expose analytics through an authenticated internal dashboard.

Add recommendations progressively through batch-generated product lists and lightweight ranking functions. Train future models locally or in occasional batch jobs.

**The primary conversion metric is an outbound marketplace click, never an assumed purchase.**

The initial production release includes:

- Static catalogue and product pages.
- Filters, lexical search, and semantic search.
- Multiple marketplace offers per canonical product.
- Anonymous, privacy-conscious event collection.
- Basic analytics dashboard and scheduled aggregation.
- Data export, retention, and recovery procedures.

It excludes carts, checkout, order management, mandatory customer accounts, a product-editing CMS, and advanced recommendation models.

### Phase terminology

The requirements use “phase” in two ways. This plan distinguishes:

- **Release A:** Initial production version, encompassing implementation phases 0–4.
- **Release B:** Richer analytics and basic recommendations.
- **Release C:** Personalization, advanced ranking, and demand models when justified.

Semantic search and tracking are part of Release A, even though they have separate implementation phases.

## 4. Detailed data flow

### 4.1 Product publishing

1. Edit a product JSON file and add source images.
2. Validate IDs, required fields, currency, taxonomy, image references, and offer URLs.
3. Generate responsive image variants.
4. Generate static product/category pages and search metadata.
5. Hash each product’s embedding input.
6. Re-embed only products whose semantic text changed.
7. Produce a versioned manifest linking catalogue, embeddings, and search configuration.
8. Deploy matching frontend and API artifacts.
9. Run smoke checks.
10. Retain the previous release for rollback.

A price-only update does not require re-embedding because numerical price filtering uses structured fields.

### 4.2 Browsing

Pages and images load from static hosting. Ordinary catalogue browsing requires no database query.

Filters can run against a compact public catalogue index in the browser.

### 4.3 Searching

1. The visitor submits a query.
2. The API validates and normalizes it.
3. A deterministic parser extracts supported constraints.
4. Structured filters identify eligible products.
5. Lexical and semantic retrieval score those products.
6. The API returns ranked IDs, filter interpretation, and search-version metadata.
7. The browser renders results.
8. If analytics is permitted, the browser records one displayed-search event and subsequent result clicks.

A search API invocation is an operational request; a search displayed to a visitor is an analytics event. Keep them distinct.

### 4.4 Marketplace navigation

Each button is a normal link to an approved marketplace URL.

On activation, the browser sends a small analytics event using `sendBeacon` or `fetch` with `keepalive`, without delaying navigation.

If tracking fails, marketplace navigation still works.

This approach can undercount clicks, particularly with blockers or rapid navigation. Report that limitation. Do not create duplicate client-click and redirect-click conversion records.

### 4.5 Analytics and future ML

```text
Browser events
→ validation and deduplication
→ accepted raw events in D1
→ scheduled aggregates
→ dashboard

Accepted raw events
→ verified private archive
→ cleaning and features
→ time-based training datasets
→ offline evaluation
→ approved artifact
→ deployed recommendation/ranking behavior
```

No queue is required initially. Acknowledge event batches only after their database write succeeds; clients can retry using unchanged event IDs.

## 6. Anonymous identity and privacy

Use random first-party identifiers, with no fingerprinting or cross-device matching.

### Identity behavior

| Context | Behavior |
|---|---|
| No persistent tracking permission | Keep personalization state in memory for the current page/session |
| Permitted persistent analytics | Store a random visitor ID with a bounded lifetime |
| Returning browser | Reuse that browser’s permitted ID |
| Storage unavailable | Fall back to in-memory state |
| Private browsing | New context; no attempt to recover identity |
| Another browser/device | Different visitor |
| Cleared storage | New visitor |

A proposed session ends after 30 minutes of inactivity. Implement this with activity timestamps; do not depend on an unload event.

A visitor ID identifies a browser context, not a person. Distinct-ID counts should be labeled accordingly.

### Privacy defaults

- Treat persistent behavioral IDs as pseudonymous data.
- Avoid names, email addresses, phone numbers, precise location, and fingerprinting.
- Do not persist IP addresses in the behavioral dataset.
- Use transient network information only where needed for abuse protection.
- Strip query strings from recorded page URLs.
- Retain only allowlisted campaign parameters.
- Redact likely personal information from search text before storage.
- Avoid request-body logging.
- Explain that search text is sent to the embedding provider to answer the request.

Adopt an opt-in default for persistent behavioral tracking until the applicable consent requirements are established. Visitors who decline should retain full catalogue and search functionality.

India’s privacy rules and their commencement provisions need to be assessed against the actual business and audience; first-party storage does not itself establish compliance. [Official MeitY rules publication](https://www.meity.gov.in/documents/act-and-policies/digital-personal-data-protection-rules-2025-gDOxUjMtQWa?pageTitle=Digit)

### Proposed retention

| Dataset | Retention |
|---|---:|
| Persistent visitor identifier | 90 days before rotation/expiry |
| Recent personalization profile | Maximum 90 days |
| Raw accepted events in D1 | 30 days |
| Raw accepted events in private R2 | 180 days total |
| Redacted search text | 90 days; remove from older archives |
| Non-identifying daily aggregates | 24 months |
| Operational logs | 7–14 days |
| Backup generations | 30 days |

Implement retention across exports, datasets, and backups—not just the live database.

Provide “Reset personalization” and “Delete this browser’s history.” Require proof of possession of a first-party deletion credential rather than accepting an arbitrary visitor ID.

For archive deletion, maintain manifests identifying affected partitions, rewrite those partitions, and prevent deleted records from reappearing during restoration.

Raw data availability for ML means a documented rolling training window, not indefinite retention.

### Measurement semantics

- Count product views once per page-view instance.
- Count an impression after at least 50% visibility for one second.
- Deduplicate impressions within the same page-view and placement.
- Record user activations rather than raw DOM click callbacks.
- Infer sessions from activity.
- Measure active engagement only while visible and recently active.

- Send small batches, for example up to 10 events and 16 KB.
- Retry transient failures with backoff and unchanged event IDs.
- Bound local retries and expiration.
- Make `event_id` unique in storage.
- Accept at-least-once delivery with deduplication.
- Record missing telemetry as a measurement limitation.

## 9. AI search architecture

### Recommended search strategy

Use:

1. Deterministic constraint extraction.
2. Structured filtering.
3. Lexical relevance.
4. Embedding similarity.
5. Deterministic score fusion.

Do not use a generative LLM or managed vector database initially.

### Product embeddings

Construct semantic text from:

- Product name.
- Category/subcategory.
- Material, color, fit, season, occasion.
- Tags and useful description.

Exclude URLs, internal IDs, private data, and numerical price constraints.

Store:

```text
product_id
embedding_model
embedding_dimension
text_hash
embedding_version
catalogue_version
normalized_vector
```

At 60 products and 384 dimensions:

```text
60 × 384 × 4 bytes = 92,160 bytes
```

The raw float32 matrix is approximately 90 KiB before metadata. Exact similarity is inexpensive at this size.

### Query interpretation

For:

> show me something casual for summer under 800

Extract:

```text
occasion: casual
season: summer
price constraint: less than INR 800
semantic intent: casual lightweight summer clothing
```

Define language precisely:

- “Under 800” means `< 800`.
- “Up to 800” means `<= 800`.
- “Between 500 and 800” uses inclusive boundaries.
- Currency defaults to INR only when the site clearly establishes it.

Use dictionaries and tested parsing rules for category names, synonyms, colors, common occasions, and price expressions.

Support straightforward negation such as “not black.” When interpretation is uncertain, show editable filter chips rather than silently enforcing a guess.

### Retrieval and scoring

1. Remove inactive products.
2. Apply reliable hard constraints.
3. Calculate lexical ranking.
4. Obtain a query embedding.
5. Calculate cosine similarity over eligible products.
6. Fuse lexical and semantic ranks.
7. Return a bounded result set.

Use rank-based fusion initially to avoid pretending lexical scores and cosine similarity share a calibrated scale.

Do not force results merely because every vector has a nearest neighbor. Establish a relevance threshold using a hand-labeled evaluation set.

If a strict budget produces no matches, display that result. Offer broader suggestions separately without silently breaking the constraint.

### Cost controls

- Generate catalogue embeddings only when semantic content changes.
- Cap query length, for example 200 characters.
- Search on submission; avoid embedding every keystroke.
- Cache only sanitized query embeddings/results with a bounded TTL.
- Include model, catalogue, filter, and search versions in cache keys.
- Treat edge cache hits as optional optimizations, not globally guaranteed.
- Apply per-client and aggregate usage limits.
- Disable semantic calls through a feature flag if a budget threshold is crossed.

### Fallback behavior

If hosted embeddings are slow, unavailable, or rate-limited:

- Return lexical results with the same hard filters.
- Record a fallback flag when analytics is permitted.
- Preserve a usable search experience.

### Local versus hosted models

Use hosted embeddings initially for consistent product/query vectors and minimal deployment work.

Local product embedding generation becomes useful if provider dependence matters. It requires the same model, preprocessing, pooling, and normalization as query embeddings. Validate parity before mixing implementations.

Avoid downloading an embedding model into every visitor’s browser: the transfer and device cost are disproportionate for this catalogue.

No small generative model or paid reranker is needed at launch.

### Search acceptance gate

Build a 40–60-query benchmark covering:

- Exact product names.
- Category and attribute combinations.
- Natural-language requests.
- Price boundaries.
- Negation.
- Typos.
- Empty results.
- Ambiguous queries.

Require:

- No known hard-filter violations.
- No inactive products.
- Acceptable top-five relevance on labeled queries.
- Correct fallback behavior.
- Measured latency on mobile networks.

Support Hindi/Hinglish only after testing a multilingual model and representative queries; do not assume an English model handles them adequately.

## 10. Analytics architecture and metric definitions

Run an incremental aggregation job hourly or nightly. Nightly processing is sufficient initially.

Use `received_at` for ingestion checkpoints and `occurred_at` for behavioral reporting. Validate clock skew and bound late arrivals.

Recompute recent affected partitions, such as the previous three days, to incorporate late events. Use deterministic upserts so retries do not double-count.

### Core metrics

| Metric | Definition |
|---|---|
| Tracked visitors | Distinct permitted browser IDs in the selected period |
| Sessions | Distinct inferred sessions in tracked data |
| Product views | Deduplicated `product_view` events |
| Marketplace clicks | Deduplicated marketplace activations |
| Product-view-to-click rate | Sessions that viewed a product and subsequently clicked its offer ÷ sessions viewing that product |
| Marketplace button CTR | Page-view/offer exposures with a later click ÷ visible page-view/offer exposures |
| Marketplace share | Marketplace clicks for that platform ÷ all marketplace clicks |
| Search-to-product-click rate | Displayed searches with a result click ÷ displayed searches |
| Zero-result rate | Displayed searches with zero eligible results ÷ displayed searches |
| Poor-result proxy | Searches with no clicks, rapid reformulation, or low evaluated relevance |
| Exploration time | Estimated active time, when engagement measurement is enabled |

For view-to-click attribution, require the same product and session with the click after the view, within a declared window such as 30 minutes.

Direct card-to-marketplace clicks belong in overall outbound clicks but not a product-detail-view funnel without a preceding product view.

### Business questions

- **Popular products:** views, unique viewers, and clicks.
- **High views, low clicks:** examine eligible offers, visible buttons, price, and sample size.
- **Popular categories:** category traffic and product interaction grouped by taxonomy.
- **Marketplace preference:** show both raw share and exposure-adjusted CTR.
- **Frequently searched products:** separate explicit product-name searches from result clicks.
- **Co-viewed products:** distinct product pairs within sessions, capped to reduce bot/session dominance.
- **Rising/declining interest:** compare normalized recent windows and show counts.

Button ordering, availability, and price differences influence marketplace choice. Raw click share is observed selection under the current UI, not an unbiased platform preference.

All metrics describe the tracked population. They may exclude non-consenting visitors, blockers, bots filtered out, or lost events.

### Progression

1. Editorial and category lists.
2. Popular products with smoothing.
3. Similar products from existing embeddings.
4. Session-based content preferences.
5. Co-view statistics.
6. Collaborative or hybrid models only after evaluation.

### Cold-start handling

|---|---|

| Returning anonymous visitor | Recent permitted preferences mixed with popular items |
| One or two interactions | Light context boost; avoid over-personalization |

popular_by_category[category_id] → ordered product IDs
trending_products → ordered product IDs

A session preference vector can later be a weighted average of viewed product vectors. Compute it in the browser first where practical.

### ML readiness

There is no universal interaction count that makes ML worthwhile.

A reasonable investigation point is several thousand clean interactions, meaningful coverage across products, and sufficient repeat browsing to evaluate behavioral patterns. This is not a production gate by itself.

Require:

- Better performance than popularity/content baselines.
- A time-based holdout.
- Adequate interaction coverage.
- Stable improvements across categories.
- No disproportionate popularity bias.
- Acceptable operational complexity.

Sparse anonymous return visits may make content-based recommendations the best long-term solution.

### Training pipeline

```text
Versioned raw data
→ cleaning and bot filtering
→ time-correct features
→ train/validation/test periods
→ candidate model
→ offline evaluation
→ approved artifact
→ deployment
→ monitored outcomes
```

Train locally initially. Deploy product lists, compact weights, or item vectors.

Local training is cheapest but depends on the owner’s machine and discipline. Move to scheduled batch compute when reliable unattended execution becomes valuable.

## 12. Future ranking and experiments

Keep search relevance separate from catalogue popularity.

### Initial rules

For search:

```text
Eligibility filters
→ lexical/semantic relevance
→ small tie-breakers for freshness or popularity
```

For category browsing:

```text
Availability
→ smoothed recent popularity
→ recency
→ diversity
```

For homepage modules:

```text
Editorial/category coverage
→ aggregate interest
→ optional session preference
```

Never let a popularity boost override a strict filter.

### Smoothed CTR

Use:

```text
smoothed CTR = (clicks + prior_strength × prior_CTR)
               / (eligible exposures + prior_strength)
```

Choose the prior from observed site/category performance. Show support counts and mark low-volume results.

Do not treat an unexposed product as a negative preference.

### Future learning-to-rank

Record:

- Candidate/list context.
- Displayed products and positions.
- Ranking/model version.
- Exposure and later interactions.
- Features available at decision time.

These are necessary to reason about position bias and avoid future-feature leakage.

### A/B testing

- Use stable assignment within the permitted browser/session context.
- Log exposure when a variant is actually shown.
- Define a primary metric and guardrails before launch.
- Exclude internal traffic.
- Avoid multiple overlapping experiments initially.
- Estimate sample size before interpreting results.

For illustration, detecting a change from 5% to 6% with conventional 5% significance and 80% power requires roughly 8,000 independent observations per arm. Real requirements depend on the assignment unit and metric. At this traffic level, small effects can take months to measure.

## 13. Future demand and trend architecture

Call initial outputs **website interest indicators**, not sales forecasts.

### Proposed interest score

For a seven-day window:

```text
InterestScore =
100 × (
  0.30 × normalized log unique product viewers
+ 0.40 × normalized log unique outbound-click sessions
+ 0.20 × normalized log attributed search-result clicks
+ 0.10 × bounded, smoothed growth
)
```

These are starting heuristic weights, not learned probabilities.

Normalize within an appropriate category where possible. Apply minimum support thresholds and decay older observations.

Keep unfulfilled search demand as a separate query/category signal instead of arbitrarily assigning it to products.

### Trend outputs

- Seven-day and 28-day product views.
- Marketplace clicks over time.
- Interest per 100 tracked sessions.
- Recent versus previous-window growth.
- Category share of interest.
- Search gaps.
- Low-confidence or insufficient-data labels.

Normalizing by overall traffic helps distinguish a product trend from a site-wide traffic spike.

### Inventory extension

Only introduce inventory forecasts after receiving:

- Variant/SKU mapping.
- Current stock.
- Sales or shipment history.
- Returns/cancellations.
- Replenishment lead times.
- Stock observation timestamps.
- Knowledge of whether inventory is shared across marketplaces.

A basic later estimate is:

```text
days of cover = usable stock / estimated daily unit sales
```

Return “insufficient data” when a defensible sales rate is unavailable.

Website clicks can flag products for review, but cannot establish how many units remain or when stock will run out.

## 15. Security architecture

### Public API

- HTTPS only.
- Same-origin API routing.
- Explicit CORS policy; CORS is not authentication.
- JSON content-type checks.
- Strict schema, length, and batch-size limits.
- Parameterized SQL.
- Product and offer validation against the catalogue.
- Limits on timestamp skew and retries.
- Rate limiting before embedding calls.
- Short-lived abuse keys; no permanent behavioral IP storage.

Start with conservative per-client limits and measure real use. Distributed edge limits are protective controls, not necessarily exact global spend caps.

### Abuse and cost protection

- Cap query tokens and API work per request.
- Maintain an aggregate embedding-use counter/budget gate.
- Add a semantic-search kill switch.
- Monitor rejected events and abnormal marketplace-click bursts.
- Use challenges only for suspicious traffic where practical.
- Do not mistake a public client token for a secret.

### Marketplace URLs

- Maintain approved marketplace hostnames.
- Accept only HTTPS URLs.
- Do not accept arbitrary redirect destinations.
- Do not fetch user-supplied URLs server-side.
- Avoid forwarding visitor/session IDs to marketplaces.

### Private data

- No public D1 credentials.
- No public R2 raw-data buckets.
- No analytics data in static build output.
- Read access limited to the private API.
- Worker secrets and narrowly scoped deployment credentials.
- Separate development and production resources.
- No production raw datasets committed to Git.

### Recovery

- Daily verified raw-event export.
- Versioned catalogue and artifact manifests.
- Documented database/schema recovery.
- Quarterly restore exercise.
- Restore workflow reapplies deletions.
- Target a 24-hour analytics recovery point and same-business-day recovery.

The static catalogue should remain available during an analytics outage.

## 16. Performance architecture

### Public pages

- Generate product/category HTML ahead of time.
- Use responsive AVIF/WebP images with fallback.
- Generate image variants during publishing.
- Set dimensions to prevent layout shift.
- Load the primary image promptly.
- Lazy-load below-the-fold images.
- Avoid external marketplace embeds.

### Cache policy

| Content | Policy |
|---|---|
| Hashed JS/CSS/images | Long-lived immutable |
| Product/category HTML | Revalidate through deployment/versioning |
| Public catalogue index | Versioned |
| Search results | Short-lived and catalogue/model keyed |
| Public recommendation lists | Versioned or short-lived |
| Private dashboard responses | Private; no shared caching |
| Personalized results | Never shared-cache across visitors |

### Targets

Treat these as acceptance targets to verify:

- Mobile p75 LCP below 2.5 seconds.
- CLS below 0.1.
- Minimal catalogue-page JavaScript, preferably below 100 KB compressed.
- Typical semantic search under 1.5 seconds end to end.
- Lexical fallback within a bounded timeout.
- Marketplace navigation unaffected by telemetry availability.

Add sitemap, canonical URLs, useful titles, accessible controls, and structured product information that accurately reflects the available data.

Lambda has ongoing free compute/request allowances, but storage, requests, logging, and related services remain separate considerations. ## 21. Scaling considerations

Scale in response to measurements.

| Trigger | Change |
|---|---|
| Free Worker CPU limit exceeded | Move to Paid; profile parser/scoring |
| Raw-event database growth | Shorten hot retention and verify archives |
| Dashboard queries scan too many rows | Add targeted aggregates/indexes |
| Ingestion latency or loss increases materially | Introduce a managed queue |
| Vector matrix affects bundle/memory/latency | Benchmark external vector index |
| Long-range analysis slows D1 | Analyze R2 exports with DuckDB or a warehouse |
| Local training becomes operationally unreliable | Scheduled batch compute |
| JSON editing becomes cumbersome | CSV import or later headless CMS |
| Relational requirements become complex | Evaluate Postgres |

Consider a vector index when there are thousands to tens of thousands of products and measurements show a benefit—not at an arbitrary visitor count.

Keep these interfaces stable:

```text
search(query, filters, context) → ranked products
recommend(context) → ranked products
recordEvents(batch) → acknowledgement
getAnalytics(range, dimensions) → metrics
```

Use adapters when an alternative actually appears; do not build a provider abstraction framework now.

## 23. Build now, extension points, and difficult decisions

### Build now

- Stable product and offer IDs.
- Validated JSON catalogue.
- Static product pages and optimized images.
- Multiple marketplace links.
- Hybrid semantic search.
- Search evaluation dataset.
- Core event tracking.
- Explicit metric definitions.
- Private analytics dashboard.
- Aggregation, archive, retention, and deletion.
- Deployment/version manifests.
- Budget controls and fallback behavior.

### Extension points only

- Recommendation provider contract.
- Model/version fields.
- Experiment context fields.
- Dataset export format.
- Variant-aware inventory mapping.
- Ranking feature boundaries.

### Defer entirely

- Collaborative filtering.
- Feature store.
- Online model training.
- Managed ML platform.
- Vector database.
- Message queue.
- Customer accounts.
- Inventory forecasting without source data.
- Product-editing admin panel.

### Decisions expensive to repair later

| Decision | Why it matters |
|---|---|
| Canonical product/variant IDs | Historical interactions must survive catalogue edits |
| Event semantics | Incorrect events cannot reliably be repaired after collection |
| Deduplication | Duplicate conversions corrupt historical metrics |
| Consent and retention | Unlawfully or unnecessarily retained data cannot be fixed by a new schema |
| Exposure and attribution rules | Required for meaningful CTR and ranking evaluation |
| Catalogue/model versioning | Historical outcomes need reproducible context |
| Currency and timezone rules | Inconsistency causes systematic reporting errors |
| Raw export format | Enables training and migration |
| Private/public separation | Prevents accidental analytics disclosure |
| Sales provenance | Distinguishes observed purchases from inferred interest |

### Requirements needing correction or qualification

1. Marketplace clicks are not purchases.
2. Browser IDs are not unique people.
3. Embeddings alone do not enforce budgets or exact attributes.
4. Offline product embeddings still require a query representation at search time.
5. Similarity search does not require a vector database.
6. Session-end events are unreliable.
7. Daily distinct visitors cannot be summed into monthly visitors.
8. Click share is affected by button exposure, order, and availability.
9. A zero-result query does not identify demand for a particular existing product.
10. Behavioral data alone cannot forecast stock depletion.
11. Unlimited raw retention conflicts with data minimization.
12. Low traffic limits reliable experimentation and collaborative learning.
13. Free-tier quotas are not availability guarantees.
14. Prices and availability across marketplaces may diverge.
15. “ML-ready” requires good data contracts and evaluation, not prebuilt ML infrastructure.

## 24. Final recommended architecture

**Use Astro and TypeScript for a statically generated catalogue on Cloudflare Workers Static Assets. Maintain one JSON document per canonical product, containing an extensible list of marketplace offers.**

**Use a small Worker for hybrid lexical/semantic search and event ingestion. Generate product embeddings during publishing, embed queries through Workers AI, and perform exact similarity over the small catalogue. Apply explicit constraints independently of embeddings.**

**Use D1 for recent accepted events and aggregates, private R2 for bounded raw archives, and scheduled jobs for aggregation and retention. Protect the internal analytics application with Cloudflare Access and API-level identity validation.**

**Launch with implementation phases 0–4. Plan for approximately $5/month in production infrastructure, with a free deployment possible if measured execution stays within free limits. Add recommendations through small batch artifacts, and introduce trained models only after they outperform simple baselines.**
